# 農業用コンテナシェアリング デモ 仕様書

用途：展示会・講演での実演／疑似データによる操作可能なデモ

## 1. デモの位置づけ

このデモは、展示会・講演の場で来場者に短時間で理解させるための道具であり、製品の先行版ではない。証明する対象は「現場の困りごとが地図の上で解ける」ことに限定する。

### 扱う課題

2026年8月の現場ヒアリングで確認された内容に基づく。

- コンテナを探すために多数の関係先へ連絡を取る必要がある
- 探索そのものに時間を要している
- コンテナは組織間を転々とするため、所有・所在が不明確になる

### 示すこと

- 位置・種類・稼働ステータスを一枚の地図で把握できる状態
- 拠点ごとの余剰と不足が、電話をかけずに見える状態

### 示さないこと

- 費用を誰が負担するかという事業構造。ヒアリング時点で未確定であり、実装では解けない
- 実在組織の実データ。すべて疑似データであり、その旨を画面上に常時表示する
- 予約・シェアの実行、紛失防止アラート。構想として提示するに留める（第6節）

## 2. 展示のストーリー

90秒で完結する一本の流れを設計し、その流れに必要な機能だけを実装する。来場者が自分で触る場合も、同じ順に進むよう画面を配置する。

| 時間 | 画面上の動き | 説明者の言葉 |
| --- | --- | --- |
| 0–15秒 | 十勝全域の地図に、コンテナが点で散らばる。拠点は円で示す | いまコンテナがどこにあるか、誰も一覧では持っていません |
| 15–35秒 | 時間スライダーを動かすと、点が収穫期に向けて偏っていく | 季節が進むと、特定の拠点に滞留します |
| 35–60秒 | 「過不足表示」に切替。余剰拠点と不足拠点が色で分かれる | 余っている場所と足りない場所が、この時点で分かります |
| 60–80秒 | 不足拠点をクリックすると、近い余剰拠点からの候補が線で表示される | 電話をかける代わりに、ここから探せます |
| 80–90秒 | ステータスの内訳を右パネルで表示 | 種類や状態の違いも同じ地図で扱えます |

### 設計上の要点

- 最初の一画面で意味が通ること。ログイン画面やメニューから始めない
- 説明者が話している間、画面は自動で動かない。操作は必ず人の手による
- 60秒地点の「候補の線」が山場。ここだけは動きを丁寧に作る
- 30分放置されても初期状態に戻る。無操作120秒でリセットする

## 3. 画面仕様

画面は一枚。左に地図、右に幅320pxのパネル、上部にモード切替と時間スライダーを置く。画面遷移は持たない。

### 3.1 地図表示

| 要素 | 仕様 |
| --- | --- |
| 対象範囲 | 十勝管内（おおむね東経142.5〜144.2、北緯42.3〜43.5）。初期ズーム9 |
| 拠点 | 円マーカー。半径は保有台数に比例（最小8px、最大28px） |
| コンテナ | ズーム11以上で個体を点表示。それ以下は拠点に集約 |
| 種類 | 3種（大型鉄コンテナ／小型コンテナ／パレット型）を色相で区別 |
| 稼働ステータス | 稼働中／空き／輸送中／点検中の4値。マーカーの塗り分けで表現 |
| 背景地図 | 淡色。農地・道路が判別できる程度に留め、彩度を落とす |

### 3.2 過不足の可視化

上部の「在庫表示／過不足表示」で切り替える。過不足表示では拠点ごとに次を計算し、色で示す。

```
在席数 = その拠点にあるコンテナ数 − 点検中
引当数 = min(在席数, 当日の想定必要数)   → 稼働中
空き   = 在席数 − 引当数
未充足 = 当日の想定必要数 − 引当数
過不足 = 空き − 未充足 = 在席数 − 当日の想定必要数
```

想定必要数を先に稼働へ引き当て、引き当てきれない分を未充足とする。需要が満たされた拠点では未充足が0となり過不足は空きに一致し、満たされない拠点では空きが0となり過不足は未充足の符号を反転した値に一致する。画面側では在席数を「空き＋稼働中」として数え、日次データの `demand` を引いて求める。

- 正の値（余剰）は寒色、負の値（不足）は暖色。0近傍は無彩色
- 円の大きさは絶対値に比例させ、大きく外れている拠点が目に入るようにする
- 不足拠点をクリックすると、直線距離が近い順に余剰拠点を最大3件、地図上に線で結ぶ
- 線には距離と融通可能台数を添える。所要時間や費用は算出しない

### 3.3 時間スライダー

- 期間は8月1日から10月31日までの92日。1日単位で移動
- 再生ボタンで1秒あたり3日進む。停止時はその日の状態を保持
- 日付が進むと稼働ステータスと配置が変化し、収穫期に向けて偏在が拡大する

### 3.4 右パネル

- 選択中の拠点名、保有台数、種類別内訳、ステータス別内訳
- 未選択時は全体サマリ（総数、稼働率、不足拠点数）
- 最下部に「本画面のデータはすべて架空のものです」を常時表示

## 4. 疑似データ仕様

データはすべて架空とし、実在の組織名・施設名を使わない。一方で、十勝を知る来場者が見て違和感を持たない配置にする必要がある。地名は実在の市町村名を用い、拠点名は「音更 第1集荷拠点」のように機能を表す名称とする。

### 4.1 規模感

| 項目 | 値 | 根拠・考え方 |
| --- | --- | --- |
| 拠点数 | 24 | 十勝管内の主要な市町村に1〜3か所ずつ |
| コンテナ総数 | 1,200 | 1拠点あたり平均50。描画負荷が実用的な上限に収まる |
| 種類 | 3 | 大型鉄コンテナ／小型コンテナ／パレット型 |
| 期間 | 8月1日〜10月31日 | 収穫期に偏在が拡大する様子を見せる |

### 4.2 生成のルール

#### 配置と移動

- 拠点は帯広市を中心に、音更・芽室・幕別・士幌・本別など実在の市町村の市街地近傍に配置する
- 8月上旬は各拠点にほぼ均等に分布させる
- 9月中旬以降、畑作地帯の拠点で空きが減り、周辺部の拠点で滞留が生じるよう重みを与える
- 全体の10%程度は常時「輸送中」とし、拠点間の経路上に置く
- 乱数種を固定し、何度開いても同じ状態が再現されるようにする

偏在は、拠点ごとの在庫目標シェアを季節係数で動かし、その差を日々の移動で埋めることで作る。畑作中核の拠点は収穫期に向けてシェアが下がり、山間・港湾寄りの拠点は上がる。輸送中の比率が規定に満たない分は、近隣拠点間の通常の循環で補う。

#### 想定必要数と引き当て

- 拠点ごと・日ごとに想定必要数 `demand` を生成する。`demand = 保有台数 × 拠点別ピーク係数 × 季節係数 × 揺らぎ`
- 季節係数は8月上旬の0.18から立ち上がり、9月25日に1.0のピークを打ち、10月下旬に0.27まで下がる正規分布状の曲線とする
- 拠点別ピーク係数は、畑作中核の拠点で1.00〜1.15、中間の拠点で0.50〜0.75、山間・港湾寄りの拠点で0.20〜0.35
- 揺らぎは0.9〜1.1の一様乱数
- `demand` と空きコンテナ数を独立に乱数生成しない。先に `demand` を決め、その拠点に在席するコンテナから引き当てて「稼働中」とし、残りを「空き」とする。引き当てきれない分が不足となる
- 引き当ての前に、在席分の3%程度を「点検中」として除く

#### 生成後の集計出力

生成スクリプトは標準出力に次を出し、分布が季節で変わっていることを確認できるようにする。

- 拠点ごとの8月平均在庫と10月平均在庫、およびその増減
- 9月25日時点の拠点ごとの想定必要数・空き・過不足
- 日付ごとの不足拠点数と余剰拠点数。過不足が −5台以下を不足拠点、+5台以上を余剰拠点とする
- 完成条件の判定。9月20日から9月30日までの各日で、不足が3〜5拠点かつ余剰が5拠点以上であること。満たさない場合は終了コードを1とする

### 4.3 もっともらしさの担保

現物の稼働データは当社に無いため、台数・拠点数は仮置きとする。実在組織を想起させる名称を画面上に置かないことだけ守る。

### 4.4 データ形式

- 拠点：GeoJSON FeatureCollection（Point）。`id` `name` `city` `capacity`
- コンテナ：JSON配列。`id` `type` `homeBaseId`
- 日次状態：92日分をgzip圧縮したJSONで同梱。日付と拠点の配列を先頭に置き、以降は添字で参照する列指向の形式とする
- ファイル総量は10MB以内に収める

日次状態の構造は次のとおり。

```
{
  "meta":       { 乱数種、ステータス名、種類定義、過不足の閾値 },
  "dates":      ["2026-08-01", ...],            // 92日分
  "baseIds":    ["obihiro-1", ...],             // 24拠点分
  "demand":     [[92日分の想定必要数], ...],     // 24拠点分
  "containers": [{ "id":     "C0001",
                   "base":   [92日分の拠点添字。-1は輸送中],
                   "status": [92日分のステータス添字] }],
  "transit":    { "<containerId>": { "<日の添字>": [lng, lat] } }
}
```

- ステータスは `稼働中` `空き` `輸送中` `点検中` を0〜3の添字で持つ
- 拠点に在席するコンテナの座標は拠点座標を用いるため保持しない。`transit` は輸送中の日のみ疎に持つ

## 5. 技術構成とデプロイ

全体を静的サイトとして構成し、GitHub Pagesに置く。サーバー側処理を持たないため、会場でローカル起動に切り替えることもできる。

| 層 | 採用 | 理由 |
| --- | --- | --- |
| ビルド | Vite + React + TypeScript | 単一ページで完結し、開発時の反復が速い |
| 地図 | MapLibre GL JS | ベクタタイルを扱え、ライセンス上の制約が少ない |
| 背景タイル | PMTiles（十勝域のみ、ズーム6〜13） | 単一ファイルで配信でき、外部タイルサーバーに依存しない |
| 状態管理 | React の useState / useReducer のみ | 規模に対して外部ライブラリは不要 |
| データ | 静的JSON（同梱） | APIを持たない |
| ホスティング | GitHub Pages | 静的のため方針どおり |

### 会場ネットワークへの備え

展示会場の回線は不安定であることを前提とする。

- 外部タイルサーバーを参照しない。背景地図はPMTilesとしてリポジトリに同梱する
- ビルド成果物一式をUSBに入れ、`npx serve` でローカル起動できる状態にしておく
- フォントはシステムフォントを用い、Webフォントを読み込まない

### 動作環境

- 想定端末：ノートPC（1920×1080）および13インチ級タブレット
- タッチ操作に対応する。ボタンの最小タップ領域は44px四方
- ブラウザはChrome最新版を基準とする

## 6. スコープ外と構想の示し方

予約・シェア操作と紛失防止アラートは、今回は実装しない。ただし来場者との会話を広げるため、構想としては画面上に示す。

- 右パネル下部に「構想中の機能」として2行の説明文を置く。ボタンは置かない
- 押せないボタンを並べると、動かない製品という印象になる。文章で示すに留める
- 質問を受けた場合は口頭で補う
